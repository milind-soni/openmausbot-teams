# 工程执行领域规范（Domain: Engineering）

> **层次说明**：本 skill 只约束**工程领域的专业执行与验证纪律**；与任务编排者的接单核对、边界遵守、结构化交付清单和验收闭环由 `task-worker` skill 负责，两者叠加使用。

## 工具与环境纪律

1. **严格使用用户指定的 Harness 工具**
   - 针对具体工程任务，先核实仓库权限与**用户（或派工单）指定的 harness 工具**是否就绪，再通过该指定 harness 工具开展工程调查、答疑、代码实现与验证。
   - 若尚未指定 harness 工具，或指定工具 / 仓库权限不可用，先向编排者（或用户）明确回报缺项并请求指定，**不要擅自切换到未授权工具**。
2. **上下文完整传递与结果负责**
   - 把任务目标、边界、依赖与约束完整交给指定的 harness 工具，并对其产出结果负全责，不把未经核验的工具输出原样当结论交付。
   - 按排障需要，配合使用当前环境实际可用的 `pstack` 等辅助技能或诊断工具。

## Bug 排查与修复纪律

- **先复现，再修复，后复验**：遇到缺陷类任务，先构造或触发复现，确认根因后再修改代码，最后按同一或更严路径复验。
- **无法复现时的推进路径**：暂时无法复现时，不猜测性盲改；继续收集日志、追踪调用链或构造最小测试用例，并在交付中**严格区分「已证实的证据」与「推测 / 假设」**。

## 工程验证与状态区分

- **按任务选择验证手段**：
  - 代码修改任务：提供实际改动位置 / 链接及对应的编译、测试或运行验证步骤与结果；缺少 CI 时明确说明替代验证方式与覆盖边界。
  - 纯工程调查 / 答疑任务：提供明确的代码路径、日志来源、事实依据与推理链。
  - 多项改动集成任务：按编排者要求执行集成验证并回传集成证据。
- **三态严禁混淆**：汇报结论时必须清晰区分以下三件事，不得混为一谈：
  1. **代码已改**（仅完成改动）
  2. **验证通过**（通过了哪些测试 / 检查）
  3. **原始故障已解决**（已证实原问题场景不再复现）

## 工程专属确认红线

- 除 `task-worker` 的通用红线外，**合并代码（Merge / Push 保护分支）、生产发布、破坏性数据或环境变更**必须先上报编排者并等待用户明确确认。
